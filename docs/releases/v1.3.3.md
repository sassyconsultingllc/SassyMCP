## v1.3.3 — Non-Claude clients first-class + startup update check

### What changed

Two related polish items: clean up the Claude-flavored cosmetic bits that
made non-Claude users second-guess whether SassyMCP would work for them,
and surface available updates at server start so users don't have to ask
the LLM to check.

- **Startup update check.** Server now hits the GitHub Releases API once
  on launch (3-second timeout, network failure is silent) and reports
  the result via `logger.info` in both modes plus an inline line in the
  HTTP banner: `Update available: vX.Y.Z -> vA.B.C  (call sassy_update_check for details)`.
  The result is cached in the same per-server Updater singleton the
  `sassy_update_*` tools use, so the first LLM-side update tool call
  within 5 minutes reuses it. Opt out with `SASSYMCP_NO_UPDATE_CHECK=1`.
  Stdio mode logs the line via stderr (the JSON-RPC stream uses stdout
  and cannot host a banner); HTTP mode prints it inside the existing
  banner block.
- **Banner is now client-agnostic.** The startup banner used to read
  *"Connect from Claude Desktop (add to claude_desktop_config.json)"*
  and only that. It now reads *"Connect from any MCP client (Claude
  Desktop, Cursor, Windsurf, Cline, Grok Desktop, Continue, custom)"*
  with the same generic `mcpServers` snippet that every conventional
  client accepts, plus a pointer to the per-client templates that ship
  in `deploy/`.
- **Three new client templates** ship in the portable bundle:
  `cursor_mcp_config.template.json`, `windsurf_mcp_config.template.json`,
  `continue_mcp_config.template.json`. The first two share the standard
  `mcpServers` shape; Continue.dev gets its own `experimental.modelContextProtocolServers`
  schema. `deploy.bat` README block updated so the in-bundle setup guide
  lists every client's expected config-file location.
- **README "MCP Client Config" section** rebuilt as a 7-row table mapping
  client -> transport -> config-file path -> matching template, with
  three code blocks covering the standard `mcpServers` shape, the
  Continue.dev shape, and HTTP/Grok shape. The previous "Claude Desktop
  Config" heading had two examples and no other clients.
- **Cosmetic docstrings de-Claude'd:**
  - `sassy_tool_group_toggle` ([meta.py](../../sassymcp/modules/meta.py)) — note now describes the
    behavior in terms of `tools/list_changed` support, with Claude
    Desktop called out as a current example of a client that doesn't
    handle it (rather than the only client that matters).
  - `sassy_selfmod_restart` ([selfmod.py](../../sassymcp/modules/selfmod.py)) — reconnect note now
    enumerates Claude Desktop, Cursor, Windsurf, Cline, Grok.
  - `sassy_kill_all_sassymcp` ([process_manager.py](../../sassymcp/modules/process_manager.py)) — the
    "another program is currently using this process" lock is described
    as something any MCP client can leave behind, not just Grok/Claude
    Desktop.
  - Crosslink module docstring ([crosslink.py](../../sassymcp/modules/crosslink.py)) — now describes
    cross-session messaging as MCP-client-agnostic.

### Compatibility

- All `mcpServers`-shape clients (Claude Desktop, Cursor, Windsurf,
  Cline) work with the standard exe path config — no client-side
  modifications.
- HTTP-mode clients (Grok Desktop, custom) work via `sassymcp.exe --http`
  and a `url` config; auth via `SASSYMCP_AUTH_TOKEN` for non-loopback
  binds is unchanged.
- Continue.dev uses its own `experimental.modelContextProtocolServers`
  schema; the new template covers it.
- `.claude/skills/sassymcp-update.md` remains a Claude-Code-only slash
  command. Other clients call `sassy_update_check` / `sassy_update_apply`
  directly as regular tools — same end-state.

### What still works exactly the same

- All distribution surfaces from v1.3.2 — portable zip, standalone exe,
  license-gated one-line PowerShell, Cloudflare Tunnel quick-start.
- Updater tools, shell-interceptor hardening, safe-delete behavior, and
  the SSRF DNS-resolution fix from v1.3.2 are unchanged.
- The `sassy_update_*` tool surface is unchanged; the new startup check
  is in addition to (not instead of) the existing tool-driven flow.
