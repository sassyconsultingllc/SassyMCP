## v1.3.4 — Per-instance state dir + de-hardcoded launchers

### What changed

Two related cleanups: make it possible to run more than one SassyMCP
instance per machine without state collisions, and stop shipping
`V:\Projects\SassyMCP` paths in launcher scripts that go in the
portable zip.

- **`SASSYMCP_HOME` env var.** New override for the per-user state
  directory. Defaults to `~/.sassymcp` (no behavior change for
  single-instance users); set it per-process to give two SassyMCP
  instances on the same machine separate `persona.md`, `config.json`,
  `tokens.json`, `license.json`, `audit.log`, `audit.jsonl`,
  `crosslink.db`, `memory.db`, `tool_state.db`, `tool_usage.json`,
  and self-signed `server.crt` / `server.key`. The `_security`
  protected-paths check honors the override too — instance A cannot
  `sassy_safe_delete` into instance B's home.
- **`sassymcp/_paths.py`** — new module is the single source of truth
  for per-user paths. `_paths.HOME` resolves once at import time from
  `$SASSYMCP_HOME` or `Path.home() / ".sassymcp"`, and exposes
  `PERSONA_FILE`, `CONFIG_FILE`, `TOKENS_FILE`, `LICENSE_FILE`,
  `AUDIT_LOG`, `CROSSLINK_DB`, `SSL_CERT`, `SSL_KEY` derived from it.
  Eleven modules (`server`, `auth`, `license`, `audit`, `crosslink`,
  `setup_wizard`, `persona`, `memory`, `runtime_config`, `state_manager`,
  `_tool_loader`, `_security`) now import from `_paths` instead of
  hard-coding `Path.home() / ".sassymcp"`.
- **`start-tunnel.bat` rewritten generic.** The old version checked for
  `V:\Projects\SassyMCP\.venv\Scripts\python.exe` and ran from there —
  fine for the developer's machine, broken for everyone else who
  extracted the portable zip. The new version resolves
  `%~dp0sassymcp.exe` (the bundled exe next to itself), accepts a
  tunnel name as an argument or via `SASSYMCP_TUNNEL_NAME`, and runs
  `cloudflared tunnel run <name>` from PATH. Both the repo-root copy
  and `deploy/start-tunnel.bat` are updated.
- **`personal/` folder** for machine-specific scripts. Created and
  gitignored. Moved out of the repo root: `autostart-bridge.bat`,
  `register-autostart.ps1`, `status.bat`, and the V:-flavored
  `start-tunnel.bat`. The folder ships with a `README.md` that
  documents what belongs there and why those files can't live in the
  public repo. Existing developer machines keep their `personal/*`
  files — they're just untracked now.
- **`tools/mercury_audit_sassymcp.py` `ROOT` de-hardcoded** —
  `Path("V:/Projects/SassyMCP")` is now `Path(__file__).resolve().parent.parent`
  with `SASSYMCP_REPO` as an override. The audit script runs from any
  checkout location.
- **README "Running Multiple Instances (Dual Session)" section** — new,
  with a per-resource conflict table, a concrete local-stdio +
  remote-tunnel example showing both `mcpServers` configs side-by-side
  with different `SASSYMCP_HOME` values, the full list of files that
  isolate per instance, and what stays shared (the source tree, the
  updater stage dir, the bundled tools).
- `SASSYMCP_HOME` and `SASSYMCP_REPO` added to the README env var table.

### Compatibility

- Single-instance users see no change: `SASSYMCP_HOME` defaults to
  `~/.sassymcp` exactly as before.
- Existing `~/.sassymcp/` state files are read in place — no migration
  needed, no auto-move of files.
- Personal files (autostart wrappers, vendor-flavored launchers) that
  used to live at the repo root now live under `personal/` on the
  developer's machine. They're gitignored, so they keep working but
  no longer ship.
- The portable zip's `start-tunnel.bat` no longer references any
  specific drive letter, venv path, hostname, or named tunnel —
  pass a name as the first argument (or set `SASSYMCP_TUNNEL_NAME`).

### Known followups

- The `installer.wxs` MSI manifest still has `V:\Projects\SassyMCP\dist\Most recent extract\...`
  Source attributes throughout. The MSI was dropped as a release asset
  in v1.3.1 and the manifest is no longer wired into any build flow,
  so it's dead weight; cleanup left for v1.4.x or whenever the manifest
  is refreshed for in-house Group Policy / Intune use.
- The high-severity audit queue from v1.3.2 Mercury (ADB path validation,
  registry-write whitelist, crosslink default-bind, audit-log secret
  redaction, web_inspector skipping `validate_url`) still pending.

### What still works exactly the same

- All distribution surfaces from v1.3.3 — portable zip, standalone exe,
  license-gated one-line PowerShell, Cloudflare Tunnel quick-start.
- Updater tools, shell-interceptor hardening, safe-delete behavior, the
  SSRF DNS-resolution fix from v1.3.2, the startup update check and
  client-agnostic banner from v1.3.3 — all unchanged.
- The `sassy_*` tool surface is unchanged. `_paths.py` is internal.
