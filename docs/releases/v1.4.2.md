## v1.4.2 — sassy_shell MCP-safe timeout auto-promote

### What changed

A `sassy_shell` call with `timeout_seconds > 120` no longer blocks the MCP connection. Instead, it auto-promotes to a background session and returns a poll-able JSON handle.

### The bug

`sassy_shell` accepted any `timeout_seconds` up to its `_MAX_TIMEOUT = 300` cap and passed it straight to `asyncio.wait_for(proc.communicate(), timeout=timeout_seconds)`. The MCP client (Claude Desktop and most other JSON-RPC clients over stdio) has its own response wall around 240 seconds: if the server doesn't reply within that window, the client gives up on the request.

The server-side subprocess kept running past that wall, but the response — when it finally arrived — landed on a dead in-flight request and was silently dropped. Worse, the stdio pipe stayed busy until the original request completed, so every subsequent tool call queued behind a connection the client had already abandoned. End result: hard wedge, zombie subprocess (often a 300-second `Start-Sleep` or a long build), and no way to recover without killing every `sassymcp.exe` and restarting the host client.

### The fix

`sassymcp/modules/shell.py` defines a new constant `_MCP_SAFE_TIMEOUT = 120` (safely below the ~240s client wall). `_run_subprocess` dispatches at the top:

```python
if timeout_seconds > _MCP_SAFE_TIMEOUT:
    return await _auto_promote_to_session(shell, command, timeout_seconds)
```

`_auto_promote_to_session` spawns a fresh `shell_auto_<8hex>` background session via `session.start_session_impl`, then returns a JSON payload like:

```json
{
  "auto_detached": true,
  "session_name": "shell_auto_4f6e2c1a",
  "reason": "timeout_seconds=300s exceeds the MCP-safe ceiling (120s)...",
  "hint": "Poll output with sassy_session_read(name='shell_auto_4f6e2c1a'). ...",
  "command": "...",
  "shell": "powershell",
  "pid": 41928
}
```

The caller polls with `sassy_session_read`, sends more input with `sassy_session_send`, and stops with `sassy_session_stop` when done. Both `sassy_shell` and `sassy_shell_confirm` benefit, since the auto-promote check sits inside `_run_subprocess`.

`session.py` got a small refactor to support this: the session-spawn logic was extracted from the closure inside `register(server)` into a module-level `async def start_session_impl(name, shell, command) -> dict`. The `sassy_session_start` tool is now a thin JSON-wrapping shim around it.

### Why 120s, not 240s

The MCP client wall is approximately 240s but isn't precisely documented and may vary by transport. 120s gives a 2× safety margin and is still well above the default `timeout_seconds=30` and any reasonable single-shot command (most build steps that overrun 120s are exactly the kind of thing that should be using a session anyway). Users who explicitly need a synchronous wait between 30s and 120s can still pass `timeout_seconds=90` and get unchanged behaviour.

### Test coverage

New sandbox test `tests/test_shell_auto_promote.py` (9 assertions, 0 failures):

- `_MCP_SAFE_TIMEOUT <= 120`
- `timeout=121` returns `auto_detached:true` with `session_name`
- Auto-detach response includes a `session_read` hint
- `timeout=120` runs synchronously (boundary check)
- `timeout=30` runs synchronously and captures stdout
- `timeout=600` cleanly auto-detaches (no hang)
- Invalid shell during auto-detach surfaces `auto_detached:false` with an `error` field

Existing 147-test `test_intercept.py` suite continues to pass (no regression in delete-interceptor, blocklist, or confirm flows).

### Verification

`scripts/verify-release.ps1` will parse and execute the fenced block below:

```ps1
python tests/test_shell_auto_promote.py
python tests/test_intercept.py
```

Live MCP round-trip (after restarting the MCP host so the new code is loaded into the running process):

1. Call `sassy_shell` with `timeout_seconds=300` and any trivial command (e.g. `Write-Host hi`).
2. Expect an immediate response of the form `{"auto_detached": true, "session_name": "shell_auto_<8hex>", "hint": "Poll output with sassy_session_read..."}` — not a 240s hang followed by a dropped connection.
3. Optionally `sassy_session_read` on the returned name to retrieve `hi` from the spawned session, then `sassy_session_stop` to clean up.

Failure mode if the running process still has v1.4.1 code: the call wedges for ~240s, the response is dropped, and subsequent tool calls queue behind a dead connection. Recovery is the same as before — kill the python/uv processes and restart the MCP host.

### Compatibility

- Any existing `sassy_shell` invocation with `timeout_seconds <= 120` (which includes the default of 30) behaves identically to v1.4.1.
- Invocations with `timeout_seconds > 120` previously wedged or returned eventually-dropped responses; now they return immediately with a session handle. Callers that parsed `sassy_shell`'s output without handling the `auto_detached` key should switch to polling `sassy_session_read` for those long-running operations.
- `sassy_shell_confirm` benefits from the same fix automatically — confirmed tokens that originally specified a large `timeout_seconds` now also auto-promote.
