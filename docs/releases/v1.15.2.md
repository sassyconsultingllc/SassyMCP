## v1.15.2 — Security: SSH local-execution options bypassed the command interceptor

**Security release. Upgrade immediately.** Affects every version that shipped
`sassy_shell`. Reported externally on 2026-09-19 by 23W-8H (GitHub), ref issue
#38.

### What changed

`ssh` options whose value OpenSSH executes on the **local** machine are now
refused at the shared command validator. One guard, five tools.

### The bug / motivation

`ssh -o ProxyCommand="<anything>" user@host` executed `<anything>` locally and
passed the interceptor as a clean command. The remote host does not need to
exist or accept the connection — `ProxyCommand` runs before the connection is
made.

Two independent gaps composed into it:

1. `detect_delete_intent()` recurses into the shells listed in `_WRAPPER_CMDS`
   (`powershell`, `cmd`, `wsl`, `bash`, `sh`, `zsh`). `ssh` is not one of them,
   so nothing inside an ssh option value was ever scanned.
2. `validate_command_tiered()` downgrades block-list hits found inside quoted
   strings to tier `low`, on the reasoning that a keyword inside a string
   literal is data rather than execution. `sassy_shell` logs `low` as
   `blocklist_literal_allowed` and **runs** it. An ssh option value is always a
   quoted string, so the payload with the worst content got the most permissive
   verdict: `ssh -o ProxyCommand="rm -rf /" u@h` was classified clean.

The reporter attributed the bypass to `harden_ssh()` in `hermes_node.py`. That
function is an ergonomics shim that adds `-o BatchMode=yes` so ssh does not
block on a prompt; it is not a sanitiser and never was. The actual hole was one
layer down in the validator that `sassy_shell`, `sassy_linux_exec`,
`sassy_session_start`, `sassy_session_send` and `sassy_adb_shell` all share —
so the blast radius was five tools, not one.

Also covered: `LocalCommand` (armed by `PermitLocalCommand`),
`KnownHostsCommand`, and config-file injection via `-F` / `-o Include=`, which
reaches the same execution channel one hop out through a config that can itself
set `ProxyCommand`.

### The fix / approach

New `detect_ssh_exec_option()` in `sassymcp/modules/_security.py`, called at the
top of `validate_command_tiered()` — before the block-list loops and before the
permission-policy engine, so neither the string-literal downgrade nor
`permission.mode=bypass` nor an `allow` rule can reach past it. Returns tier
`high`, which every caller treats as a hard refusal.

Three properties that matter:

- **Scans the raw command**, not the quoted-string-stripped view. The payload is
  always quoted; stripping quotes is what caused the bug.
- **Requires an ssh-family binary *and* the option**, so unrelated commands that
  merely mention the words (`grep -o proxycommand /etc/ssh_config.bak`) still
  run. Precision is what makes a hard refusal tolerable.
- **`-F` / `Include=` refused only outside `~/.ssh`**, so real multi-config
  workflows (`ssh -F ~/.ssh/config.work`) keep working.

Refusals name ProxyJump (`ssh -J jumphost target`), which does the legitimate
jump-host job without spawning a shell.

`hermes_node.py`: `classify()` inherits the refusal through
`validate_command_tiered()`. `run_command()` re-checks anyway — under
`HERMES_AUTORUN=1` it is the only thing between a model-authored string and a
real shell, so it does not trust its caller. `harden_ssh()`'s docstring now
states outright that it is ergonomics and not a sanitiser.

### Test coverage

`tests/test_ssh_exec_guard.py` — 26 cases: every reported payload plus each
sibling option, glued/spaced/quoted `-o` spellings, wrapped invocations
(`powershell -c "ssh -o ProxyCommand=..."`), `scp`/`sftp`, config-file
injection, `~/.ssh` traversal, and a false-positive set that must keep running
(`ssh -J`, `ssh -f`, `ssh -i`, `grep -o proxycommand`, `cat ~/.ssh/config`).

One regression caught during development: `-F` must be matched
**case-sensitively**. Under `re.IGNORECASE` it also matched `ssh -f`
(go to background), which would have refused ordinary commands.


Expect `(False, 'high', \"Command blocked (safety): ...\")`.

### Compatibility

Breaking **only** for commands that relied on the bypass. `ssh -o
ProxyCommand=`, `-o LocalCommand=`, `-o PermitLocalCommand=`, `-o
KnownHostsCommand=`, and `-F`/`-o Include=` pointing outside `~/.ssh` are now
refused through the MCP tool surface. Use `ssh -J jumphost target` for jump
hosts, keep client configs in `~/.ssh/`, or run those invocations in a real
terminal.

### Known gap

`git -c core.sshCommand=`, `GIT_SSH_COMMAND`, and `rsync -e` reach the local
shell through the same channel and are **not** covered by this guard. Tracked
for a follow-up.
